# Continuous Report PDFs

Apply this pattern to PDF output in every report implementation. Use the report implementation workflow for the surrounding API, filters, permissions, and export limits.

## Document layout

- Show the full title, subtitle, and generation details on the first physical page. Repeat table column headings on every physical page, including pages generated by automatic wrapping.
- Let the renderer wrap content based on available space. Keep each group heading with its first row and each subtotal with its last row. Compute totals from the complete filtered dataset so render boundaries never reset a group.
- Use one final PDF for preview, print, and download. Add the page number in the reserved footer after all pages are assembled, using the final document's count (for example, `14 / 334`).

## Chunked rendering

For large row-based PDFs, use a cancellable browser worker and bounded render jobs. Use the item-location report as the reference for the current React PDF and pdf-lib stack:

- [PDF assembly and page carryover](../../../src/lib/reports/build-item-location-report-pdf.ts)
- [Layout and row destinations](../../../src/components/reports/ItemLocationBatchReportPDF.tsx)
- [Worker lifecycle](../../../src/lib/reports/item-location-report-pdf.ts)

1. Render an ordered window of rows as one wrapping document. Use the row immediately before the window to resolve group changes and emit the title only at the start of the report. The reference uses up to 125 rows per job. Choose and measure a bound for the report's actual layout and dataset.
2. For each nonfinal job, mark rows with named PDF destinations to identify the first row on the last physical page. Copy the earlier pages into the final document. Start the next job at that last page's first row and fill the window with new rows. Keep one provisional page's worth of rows between jobs.
3. Require forward progress and a valid row-to-page mapping before discarding a provisional page. Fail the export safely if rendering or mapping fails. Append all pages from the final job, then stamp continuous page numbers.
4. Process jobs sequentially and release each intermediate PDF after copying its completed pages. Keep the export's overall data cap and worker cancellation/timeout behavior. Fetch boundaries, render windows, and physical pages are separate concerns.

## Download filenames

- Build the filename from the translated report title and the same local generation date shown in the PDF. Use `<report title> - YYYY-MM-DD.pdf` and capture the date when the report is generated.
- Give the dialog download action the filename explicitly. For a browser-native PDF preview, also load the PDF from a URL whose final path segment is the encoded filename. The native viewer can derive its name from that URL independently of the dialog action or PDF metadata.
- Reuse [the named PDF preview URL helper](../../../src/lib/reports/named-pdf-preview-url.ts) and [its scoped service worker](../../../src/app/report-pdf-preview/worker.js/route.ts). It serves the existing local blob inline with the filename and keeps the PDF bytes in the browser. Keep the blob URL alive while the preview is open and revoke it when the preview is replaced or closed. On browsers where the worker cannot activate, the dialog download still sets the intended name.
- Check both the dialog download and the native viewer's save dialog. Verify the native filename using the viewer toolbar itself.

## Verify the output

Use a fixture that spans several jobs, including a group that crosses a job boundary and a wrapped long label. Inspect the rendered pages around a boundary and the final page. Check that each row appears once in order, subtotals appear at the true group ends, column headings appear on overflow pages, and page numbers run from 1 to the final count. Compare page density and render time at a representative export size. Keep an empty-result case and a later-job failure case so the export stays predictable when there are no rows or rendering fails.
